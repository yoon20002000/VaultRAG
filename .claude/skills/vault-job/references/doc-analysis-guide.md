# 문서 유형별 분석 가이드

vault-job start 모드 B (문서 첨부) 실행 시
첨부된 문서 유형에 따라 아래 항목에 집중하여 추출.

---

## 기획서 / 디자인 문서

```
우선 추출:
- 제목 / 기능명 → 작업명
- "구현 범위", "기능 설명" 섹션 → 작업 범위
- "완료 기준", "인수 조건", "Done 기준" → 완료 조건 체크리스트
- 등장하는 클래스명, 씬명, UI명 → scope_files 탐색 키워드
- 등장하는 기술 용어 (FSM, Addressables 등) → scope_keywords

주의:
- "향후 개선 사항"은 완료 조건에 포함하지 않음
- 디자인 의도(UX 설명)는 작업 범위에 간략히 포함
```

## 태스크 / 이슈 티켓 (Jira, Notion, Linear 등)

```
우선 추출:
- 제목 → 작업명
- Description / 본문 → 작업 범위
- Acceptance Criteria / 체크리스트 → 완료 조건 (그대로 변환)
- Labels / Tags → scope_keywords 후보
- 언급된 파일명, 컴포넌트명 → scope_files 탐색 키워드
- Linked Issues / 관련 티켓 → 참고 메모로 기록

주의:
- "Nice to have" 항목은 완료 조건에서 제외
- 담당자, 마감일 등 메타 정보는 무시
```

## 스프린트 카드 / To-do

```
우선 추출:
- 카드 제목 → 작업명
- 설명 텍스트 → 작업 범위 (짧으면 그대로)
- 하위 항목 → 완료 조건 체크리스트
- 태그 → scope_keywords

주의:
- 내용이 적을 경우 작업명에서 최대한 추론하여 보완
- 추론한 내용은 "(추론)" 표시 후 사용자 확인
```

## 코드 리뷰 / PR 설명

```
우선 추출:
- PR 제목 → 작업명
- 변경 사항 설명 → 작업 범위
- 변경된 파일 목록 → scope_files (직접 등록)
- 리뷰 체크리스트 → 완료 조건

주의:
- 이미 완료된 PR인 경우 job이 아니라 vault-sync 대상일 수 있음
  → "이 PR은 이미 완료된 작업인가요?" 확인 후 분기
```

## 기술 스펙 문서

```
우선 추출:
- 문서 제목 → 작업명 (구현 작업이 명확한 경우)
- 구현 요구사항 섹션 → 완료 조건
- API / 인터페이스 정의 → scope_keywords (클래스/메서드명)
- 의존성 / 연동 시스템 → scope_vault 후보

주의:
- 스펙 문서 자체가 구현 대상인지, 참고 자료인지 먼저 확인
  → "이 문서를 구현하는 job인가요, 참고 자료인가요?"
```

## 공통 추출 규칙

### 완료 조건 변환

문서의 다양한 표현을 체크리스트로 변환:

| 원문 표현 | 변환 |
|----------|------|
| "~해야 한다" | `- [ ] ~` |
| "~를 지원한다" | `- [ ] ~ 지원` |
| Acceptance Criteria 항목 | `- [ ] 항목 그대로` |
| "~가 동작해야 함" | `- [ ] ~ 동작 확인` |

### scope_files 탐색 방법

문서에서 클래스명, 씬명, 프리팹명이 언급되면:
```bash
# 해당 이름으로 프로젝트 내 파일 탐색
find Assets/ -name "*BossController*" -o -name "*BossPhase*" 2>/dev/null
find Assets/ -name "*BossScene*" 2>/dev/null
```
탐색 결과를 후보로 제시, 사용자가 확인.

### 추론 불가 항목 처리

문서에서 추출이 불가능한 항목:
- 빈 섹션으로 생성 후 `> [!todo] 작성 필요` 표시
- 사용자에게 해당 항목만 별도 질문
- "모르겠음" 입력 시 빈 상태로 진행

### 문서 내용이 너무 긴 경우

200줄 이상 문서는 전체를 읽지 않고:
1. 제목, 목차, 첫 섹션만 먼저 읽어 구조 파악
2. "완료 조건", "인수 조건", "Done", "Checklist" 키워드 섹션 집중 탐색
3. 필요 시 추가 섹션 읽기
